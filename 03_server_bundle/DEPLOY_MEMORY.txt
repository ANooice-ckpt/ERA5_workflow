ERA5 memory scheduler v2.1 — incremental deployment, 2026-10-14
=============================================================
以下命令沿用已经上传到 ECS 的 models/ 和 weather/；不需要重新传输约 7.64 GB 输入。
本次没有远程登录、启动 ECS 计算、修改云资源或覆盖旧结果。
仅有当前本地配置的机器需先准备科学配置；已有服务器的 config.R 会原样保留。

1. Windows 打包及传输
--------------------
在 E:\ERA5\ERA5_workflow 的 PowerShell 中执行：

  .\BUILD_CODE_UPDATE.ps1
  $ecsHost = 'ubuntu@YOUR_ECS_IP'
  scp .\02_local\audit\era5_memory_v2_code_update.tar.gz "${ecsHost}:~/era5_memory_v2_code_update.tar.gz"
  ssh $ecsHost

将 ubuntu@YOUR_ECS_IP 替换为实际 SSH 用户和地址。若使用密钥，在 scp/ssh 后加 -i '密钥路径'。
压缩包只含代码、执行配置、说明、校验清单；不包含 config.R、模型、气象数据或结果。

2. Ubuntu 解包、备份和安装
------------------------
先确认旧计算进程已经退出。不要在模型计算仍运行时更换代码。
以下使用已确认的 ECS bundle 目录；仅当实际移动过目录时才改 ERA5_DIR。
在同一个 SSH 会话中执行：

  set -euo pipefail
  ERA5_DIR=/data/era5/ERA5_workflow/03_server_bundle
  cd -- "$ERA5_DIR"
  test -f config.R && test -d models && test -d weather
  stage_dir=$(mktemp -d "$ERA5_DIR/.code_update_20261014.XXXXXX")
  tar -xzf ~/era5_memory_v2_code_update.tar.gz -C "$stage_dir"
  (cd "$stage_dir" && sha256sum -c UPDATE_SHA256SUMS.txt)
  backup_dir=$(mktemp -d "$ERA5_DIR/.code_backup_20261014.XXXXXX")
  for item in code config.R config_pilot.R config_memory.R run_server.sh README_SERVER.txt DEPLOY_MEMORY.txt SHA256SUMS.txt WEATHER_MD5SUMS.txt; do
    if [ -e "$item" ]; then cp -a -- "$item" "$backup_dir/"; fi
  done
  mkdir -p code logs
  cp -a -- "$stage_dir/code/." code/
  for item in config_memory.R config_pilot.R run_server.sh README_SERVER.txt DEPLOY_MEMORY.txt SHA256SUMS.txt WEATHER_MD5SUMS.txt; do
    cp -a -- "$stage_dir/$item" "$item"
  done
  printf 'Old code and configuration backup: %s\n' "$backup_dir"

上面的复制清单不覆盖 config.R、models/、weather/、旧 results/ 或任何检查点。
暂存目录和旧代码备份保留用于审计，不含复制的大型科研数据。
勿从旧 results 中搬入 14 个旧版本检查点：执行文件指纹已变更，禁止绕过验证。

3. 初始配置与一次自动预检
------------------------
config_memory.R 读取现有 config.R 的全部科学参数，仅覆盖执行设置和输出根目录。
默认 scheduling="memory_lpt"、workers=64（进程池上限）、autotune=FALSE、resume="auto"。
memory$reserve_fraction=0.15（至少留 4 GiB，另留主进程额度），safety_factor=1.30，backfill=TRUE，max_rebuilds=2。

初始建议（是保守估计，未在这两种 ECS 上实测）：
  32 vCPU / 128 GiB：workers=32，reserve_fraction=0.15，safety_factor=1.30，backfill=TRUE。
  64 vCPU / 256 GiB：workers=64，其余同上。
默认上限 64 在 32 vCPU 机器上也会自动降至可用 CPU 数；这不是同时启动 32/64 个大 Tile 的指令。
池大小在加载模型和每个 worker 初始化后根据实际内存复查；同时执行数由实时准入决定。
预留大 Tile 后仍允许预计能及时结束、且保留峰值后仍不挤占大 Tile 内存的小任务回填。
若全空闲且 GC 后仍无法准入，自动关闭空闲池、确认退出后以一半上限重建，重新执行逐 worker QC。
最多两次（单 worker 时允许刷新该进程）；仍失败会保留检查点并明确退出，降低 workers 后可原目录续算。

保留已有科学配置，确认 full 对应的 config.R$run$max_cells 为 NULL、day_chunk=31、
backend="cpp"、n_draws=2000，以及现有 CDD/支持域设置。不要为了通过测试修改科学阈值。
已知历史实现问题：03_run_ecs.R 仍直接将内部 global$preprocessing_acknowledged 设为 TRUE，
没有使用外层同名开关；这是既有行为，本次未混入科学层修改，不能把它当成元数据已人工核验的证据。

已有 Micromamba 环境为 /data/era5/micromamba/envs/era5，R 4.5.3。
新入口自动优先调用 micromamba run，适用于新 SSH 会话和后台 nohup，无需依赖 shell 之前是否激活。
先确认入口显示的 R 路径和版本，再运行一次预检：

  cd /data/era5/ERA5_workflow/03_server_bundle
  bash run_server.sh env
  bash run_server.sh check

如需在交互式 shell 中直接使用 Rscript，可手动激活现有环境：

  export MAMBA_ROOT_PREFIX=/data/era5/micromamba
  eval "$("$HOME/.local/bin/micromamba" shell hook --shell bash)"
  micromamba activate era5
  command -v Rscript
  Rscript --version

其他安装位置可设置 MAMBA_ROOT_PREFIX、MAMBA_EXE、ERA5_MAMBA_ENV。
ERA5_R_ENV=current 显式使用 PATH 中的 R；ERA5_R_ENV=micromamba 强制要求指定环境存在。
默认 auto 在上述环境存在时优先使用它，否则检查当前 PATH；都找不到时给出错误，不继续计算。

check 自动运行静态 SHA256、原数值回归、真实 PSOCK 合成调度测试、新内存测试、气象包校验、
依赖和配置检查。在 Linux 还检查真实 worker PID 的 /proc/cgroup 读数。
若监测失败，memory_lpt 会拒绝启动或停止新派发并等待在途任务完成，不会静默切换到无约束并行。
实际模型数值 QC 仍在每次正式入口中自动执行。这不是要求另开多轮性能 pilot。

4. 正式运行与查看进度
--------------------
新版本写入 results_memory_v2/，旧 results/ 保留不动。

  mkdir -p logs
  run_log="logs/full_memory_$(date +%Y%m%dT%H%M%S).log"
  nohup bash run_server.sh full > "$run_log" 2>&1 < /dev/null &
  launcher_pid=$!
  printf '%s\n' "$launcher_pid" > logs/memory_launcher.pid
  printf 'Log: %s; launcher PID: %s\n' "$run_log" "$launcher_pid"
  tail -f "$run_log"

tail -f 的 Ctrl+C 只退出日志查看，不会停止后台计算。
运行创建目录后，可在同一 bundle 中查看：

  run_dir=$(cat results_memory_v2/latest_run.txt)
  tail -n 5 "$run_dir/global/progress.csv"
  ls -t "$run_dir"/global/memory_dispatch_*.csv "$run_dir"/global/memory_monitor_*.csv
  ls "$run_dir/global/checkpoints"/tile_*.rds | wc -l

最后一个文件数量可能包含 *_error.rds，只作浏览；有效完成数量以 progress 和检查点验证为准。
memory_dispatch 记录实际派发/完成、原因、PID、预测与观测内存、未来增长预留、状态及检查点字节数。
memory_monitor 约每秒更新；telemetry_valid=FALSE 时数值是上一次有效采样，sample_time 给出其时间。
tile_timings 保留原分阶段计时；resume_*.csv 记录已验证并跳过的检查点及计时 sidecar 是否存在。
ETA 用分组耗时和观测并行度估计剩余工作，初期不确定性高，不包括最终汇总；不是性能保证。

5. 温和中断、恢复与最终核验
--------------------------
在 bundle 目录内请求停止新派发、等待当前 Tile 原子提交：

  run_dir=$(cat results_memory_v2/latest_run.txt)
  touch "$run_dir/STOP"

查看日志，等到队列排空且 launcher 已退出。请求停止后非零退出是正常的，已提交结果仍有效。
可用 ps -p "$(cat logs/memory_launcher.pid)" 查看同一后台 launcher 是否尚在运行。
不要用 kill -9 作为常规中断方式；强制退出后只能依赖原子提交且再次验证通过的检查点。
前台 full 的 Ctrl+C 也会请求停止派发并排空，STOP 文件更适合后台任务。

确认旧进程退出后恢复：

  run_dir=$(cat results_memory_v2/latest_run.txt)
  if [ -f "$run_dir/STOP" ]; then rm -- "$run_dir/STOP"; fi
  run_log="logs/resume_memory_$(date +%Y%m%dT%H%M%S).log"
  nohup bash run_server.sh full > "$run_log" 2>&1 < /dev/null &
  launcher_pid=$!
  printf '%s\n' "$launcher_pid" > logs/memory_launcher.pid
  tail -f "$run_log"

resume="auto" 会验证同版本、同数据/科学设置/后验配对的检查点，只派发缺失 Tile。
本版本中只改 workers、scheduling、memory 或 progress_seconds 不改变科学指纹。
本次 v2.1 更改了执行代码，755eefb 的 v2 检查点也不能强行续接；若已经运行过 v2，保留旧目录，
将 config_memory.R 的输出根目录改为一个新的 results_memory_v21 后运行，进度/STOP 命令也相应替换目录名。
改代码、科学参数、模型、R/包版本等仍可能导致指纹拒绝续算，不能强制忽略。
已完成的运行不会自动重做。需要新科研情景时另选输出根目录或显式 resume="new"。
结束后：

  bash run_server.sh verify

下载整个 results_memory_v2/，保留 global/checkpoints；不要只下载 CSV 和 PNG。
若需要 LPT 对照，在 config_memory.R 中仅把 scheduling 改为 "lpt" 并自行保守设置 workers。
该对照模式不执行内存准入，不能把 64 的池上限直接当成安全的 LPT 并发数。
